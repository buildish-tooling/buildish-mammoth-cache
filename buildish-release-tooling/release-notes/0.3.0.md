# Mammoth Cache 0.3.0

This release replaces the flat journal-based cache lifecycle with hierarchical
streaming and bounded per-directory processing. It reduces repeated local observation,
validation and metadata work while retaining exact reuse of unchanged cache objects.
The cache formats are incompatible with 0.2.x: expect cold caches and upgrade
cooperating distributed jobs together. The Actions continue to run on Node.js 24.

## Highlights

- Use versioned native partition objects, generation records, local handoffs and
  worker TAR streams. Publish changed objects before their immutable generation
  record, and reuse exact object references for unchanged partitions. Changed
  partitions still upload in full.
- Replace whole-cache journal inventories with hierarchical streaming and bounded
  directory processing. Reuse operation-local indices and validated evidence, reduce
  repeated metadata decoding and scratch reads, and skip GC replay when a sealed
  capture establishes that there are no deletion targets. These are reductions in
  work; elapsed-time gains depend on cache layout, payloads, runner and backend.
- Preserve complete Gradle Groovy, Kotlin DSL and transform workspaces, while using
  per-entry selection for eligible task-output cache archives. Keep authoritative
  dependency-metadata snapshots separate from aggregate worker contributions.
- Use guarded native moves for publication and return writable source trees within
  the same operation after SDK consumers settle. Interrupted owners are rejected;
  the lifecycle does not provide restart/replay recovery or ambiguous-upload salvage.
  Failed worker uploads can retain immutable packages at reported paths.
- Expose `cache-max-directory-entries` on both Actions. The default is `100000`
  direct entries per managed directory, independently of working-memory budgets.
  Diagnostics identify the affected phase, directory and limit.
- Retain strict incoming worker body and complete-unit validation. Preserve owned
  empty descendants of selected complete units and retire local metadata readers
  before their scratch storage closes.
- Rename verified Gradle wrapper metadata to
  `gradle-wrapper-<version>.jar.sha256` and `gradle-wrapper-<version>.jar.asc`,
  allowing custom launchers to retain Mammoth's verified wrapper JAR.

## Upgrading from 0.2.2

- Expect a cold cache. The new namespace and worker/native/generation/local formats
  do not reuse the old cache families. Upgrade all cooperating workers, aggregators
  and readers together, using consistent partition and writer settings. There is
  no old-format bridge or permanent dual-format path.
- Review the Gradle dependency-metadata writer configuration. Its complete snapshot
  must cover the dependency sets needed by downstream offline consumers; aggregating
  artifact files alone does not make an incomplete metadata snapshot sufficient.
- Use dedicated cache roots and an exclusive prepare/post window. Keep other cache
  actions and concurrent consumers from modifying the same managed trees. Gradle
  writable publication requires consumer quiescence. Preserve reported interrupted
  or retained state for diagnosis rather than expecting automatic restart recovery.
- Base change detection uses filesystem metadata. Byte rewrites that preserve the
  observed metadata may be missed; Mammoth does not maintain a per-file base content
  catalogue. Native base bytes rely on authorized producers and the cache service;
  incoming worker payload validation remains strict.
- Scripts that consume `gradle-wrapper-<version>.sha256` or
  `gradle-wrapper-<version>.asc` must use the new `.jar.sha256` and `.jar.asc` names.
  Provisioning no longer writes the previous names; existing files are left in place.
- Review unusually wide managed directories before raising the new directory-entry
  limit. A larger limit is not a guarantee of sufficient runner memory or disk.

Review the exact `v0.3.0-rc1` candidate tag and use `v0.3.0` after final promotion,
at `actions/github/gradle` or `actions/github/maven`. Ordinary source branches omit
the generated executable bundles; use a materialized release or candidate ref.
