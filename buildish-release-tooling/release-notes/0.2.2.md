# Mammoth Cache 0.2.2

This release reduces repeated filesystem, hashing and metadata-validation work during
cache restore, distributed worker application and publication. It keeps the existing
cache formats and Node.js 24 action runtime. Actual performance gains depend on the
cache layout and runner; no hosted elapsed-time speedup is claimed.

## Highlights

- Stop rehashing base-cache payloads during restore, including single-writer snapshot
  initialization. Continue checking generation/object identity, descriptor digests,
  path ownership, file membership, regular-file types and sizes. Base payload bytes
  are trusted to authorized producers and the cache service; same-size corruption
  of those bytes is no longer detected by Mammoth during restore.
- Build and index installation metadata once per stable phase. Share ancestor
  checks, move complete base workspaces where possible, avoid unnecessary permission
  and timestamp updates, and retain guarded installation and recovery handling.
- Consume disposable worker payloads with guarded moves where possible, with
  cross-filesystem copy fallback. Preserve worker payload verification and coherent
  whole-workspace selection; live cache files are not moved into worker uploads.
- Keep whole-cache publication inventories bounded independently of the number of
  saved partitions. Check the relevant partition's sources around each upload and
  retain a final complete replay and directory-topology barrier before publishing
  the generation record.
- Hash newly captured ordinary publication payloads once per finalize invocation.
  Reuse snapshot capture/verification digests only while their source identities
  remain valid. Retries rebuild local evidence and verify previously receipted
  objects by exact readback before reusing them.
- Pass validated partition descriptors forward, reuse validation of owned immutable
  publication plans, and share source-directory checks within stable operations.
  Preserve durable receipt checkpoints and record-last publication. Add publication
  work counters and timings for inventories, hashing, checkpoints and backend saves.
- Keep generated Gradle build-reporting runtime checks compatible with Node.js 24.

## Upgrading from 0.2.1

- No action-input or workflow changes are required. Cache schemas, storage families,
  worker-package formats and generation records are unchanged; existing 0.2.1 caches
  remain eligible for reuse. Upgrading does not itself force a cold cache.
- Review the base-restore trust change above. Worker imports still verify payload
  content, and store/publication retains content hashing with operation-local
  identity-bound reuse. The Gradle and Maven actions continue to use Node.js 24.
- Publication requires stable source trees. Creating or removing even an excluded
  sibling can conservatively invalidate its parent's directory evidence and reject
  publication. Keep build processes from changing managed cache trees during post.

## Remaining capacity limits

Metadata record/byte limits and worker-package size limits are unchanged. Large
retained caches or substantial dependency/Gradle-version churn can still exceed
those limits during aggregation or other lifecycle stages. These optimizations do
not resolve that capacity issue or establish support for larger cache inventories.
Changed partitions continue to upload in full; unchanged partitions are reused.

Review the exact `v0.2.2-rc1` candidate tag and use `v0.2.2` after final promotion,
at `actions/github/gradle` or `actions/github/maven`. Ordinary source branches omit
the generated executable bundles; use a materialized release or candidate ref.
