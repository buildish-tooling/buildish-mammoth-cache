This release fixes distributed Gradle cache conflicts and misleading reports from
expected child-build failures. It also enables complete artifact-transform workspace
caching by default. The cache format changes: both Gradle and Maven start cold after
upgrading, and cooperating jobs must upgrade together.

## Highlights

- Fix conflicts when independent workers generate the same Kotlin DSL workspace
  with different origin metadata. Preserve each recognized scripts/accessors
  workspace as one complete unit, including metadata, outputs and empty directories.
  Select one producer per workspace key while retaining disjoint keys from other
  workers. Legacy scripts and generated Gradle API JARs retain strict conflict handling.
- Fix conflicts between same-key Gradle build-cache archives whose origin metadata
  differs between builds. The built-in `build-cache` partition selects one producer's
  whole, unchanged archive per key; it does not unpack or normalize archives.
- Enable `transforms-metadata` by default for recognized complete transform
  workspaces under `caches/transforms-4/` and `caches/<version>/transforms/`.
  Retain metadata, outputs and empty directories together, including real output
  files named `gc.properties`. This can reuse outputs of transforms that do not
  participate in Gradle's build cache. Unknown/incomplete layouts and workspaces
  containing mandatory-excluded outputs are skipped as whole units.
- Keep whole-workspace selection deterministic by producer job name, preserve
  strict overrides, and reuse unchanged partitions. Build membership indexes once
  per partition to avoid repeated scans for every workspace. Native base publication
  continues to avoid additional payload staging copies.
- Suppress build-result capture for child Gradle builds launched by `Test` tasks,
  including TestKit fixtures that deliberately fail. The enclosing build still
  reports unexpected test failures. Document the existing child-process opt-out
  for `Exec` and other process-launching tasks.
- Extend real independent-worker regression coverage for Kotlin workspaces and
  build-cache entries. Qualify transform workspace reuse locally on Linux with
  Gradle 8.7 and 9.8.1, cacheable/non-cacheable transforms, empty/no outputs and
  relocated readers, including a JDK 25 reader for Gradle 9.8.1. This is bounded
  coverage, not universal plugin or platform qualification.

## Upgrading from 0.2.0

- Upgrade cooperating workers and aggregators together and start a new workflow
  run. Cache schema 8 and the new storage family intentionally start Gradle and
  Maven caches cold. Previous worker envelopes and local invocation state are
  incompatible; old backend entries expire normally without migration.
- Transform workspace caching is newly enabled. It adds metadata scans, payload
  hashing, archive storage and transfers, potentially alongside build-cache copies
  of the same outputs. Net performance depends on the build. To retain the previous
  disabled behavior, add this entry to the existing `cache-partitions` configuration:

  ```yaml
  - id: transforms-metadata
    enabled: false
  ```

- Captured transform outputs may contain private dependency content or sensitive
  data written by build logic, including transforms without `@CacheableTransform`.
  Ensure cache and worker-artifact readers may access those contents, or disable
  the partition. Workspace validation does not establish that outputs are secret-free.
- The built-in `kotlin-dsl` and `transforms-metadata` partitions default to
  `conflict-handling: choose-worker-directory`; `build-cache` defaults to the new
  `choose-worker-entry` policy. These select a whole producer view even if actual
  same-key outputs differ, assuming correctly declared, reproducible Gradle work.
  Set `conflict-handling: default` on the relevant partition to reject differing
  duplicates instead. Partial user selection of a complete workspace fails capture.

The Gradle and Maven actions continue to use the Node.js 24 runtime. Review the
exact `v0.2.1-rc1` candidate tag and use `v0.2.1` after final promotion, at
`actions/github/gradle` or `actions/github/maven`. Ordinary source branches omit
the generated executable bundles; use a materialized release or candidate ref.
